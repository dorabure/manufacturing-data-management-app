# Ver1.10 CSVフォルダ周期自動取込 要件定義書

状態：Ver1.10 Phase 0 設計確定（J-01=B最終反映、未実装）
基準：初版2026-09-26の設計と、ユーザーの「Ver1.10 Phase 0 設計確定・改訂指示書」および「Phase 0 最終設計改訂指示書」を適用し、後の指示を優先する。

## 1. 目的・改訂範囲

PLC／SCADA等が出力するCSVを、Windowsローカル通常フォルダから周期取込する。Ver1.00手動取込の正常行だけを登録する動作を維持し、周期取込にはファイル単位All-or-Nothingを適用する。

今回は本書と[基本設計書](V1_10_PERIODIC_IMPORT_DESIGN.md)のみ改訂する。ソース実装、DB Migration実行、既存DB変更、Form変更、テスト実装、Publish、dist更新は行わない。本文のMigration・コード変更は将来実装の設計である。

「確定」は今回のユーザー判断、「実現方式」は要求を満たす技術設計、「要判断」は新たに見つかった安全性・互換性の論点を表す。J-01=Bも確定済み。基本設計§12に確定状況を記載し、現時点でユーザー判断待ちの設計項目はない。

## 4. Validation・ファイル公開契約

| 対象 | 検証 |
|---|---|
| CSV設定 | 既存Encoding／Delimiter／ヘッダー／6項目Mappingを利用。列番号1以上・重複なし。開始時にDBから再読込 |
| 周期 | NumericUpDown Minimum=1、Maximum=604800、DecimalPlaces=0、Increment=1。空・小数・範囲外を開始時拒否 |
| フォルダ | 絶対パスへ正規化し存在・列挙・読取・移動先利用を検証。Directory.Existsだけで権限を判定しない |
| ストレージ | UNC、ドライブ割当先がNetwork、リンク／junction／reparse経由の対象を拒否。ローカル通常フォルダのみ |
| パス境界 | 対象はルート直下、移動先はsuccess/error直下。任意パスや親フォルダを操作しない |
| 保存先準備 | success/errorと管理領域を取込前に準備。確認用に新規作成した一時ファイルだけを片付ける |
| 行の業務検証 | 必須・型・範囲・CSV内重複・DB既存重複を共通利用。周期では登録に必要な設備の存在も事前確認。手動の検証挙動を変えない |
| ロック | 共有／ロック違反は対象と後続を保留し当該周期を終了、次周期に再試行。アクセス拒否、容量不足、一般I/Oエラーをすべて書込み中とは扱わない |

公開後のCSVは内容を変更しない。推奨出力は「.tmp等へ書込み→完了→Close→.csvへrename→以降変更しない」。直接.csvへ書く場合も、書込み完了までwriteハンドルを維持し、完了後は変更しない。

ガードは読取り共有のみを許して既存Adapterの読込み中も保持する。閉じたり開いたりして追記する装置の完了をロックだけで保証できない。更新時刻／サイズが安定しただけでも完成の証明にはならない。実装時は出力装置が上記契約を満たすことを確認する。

## 5. 周期取込のAll-or-Nothingと件数

全行の解析・Mapping・Validation・既存DB重複確認を終え、登録拒否理由がない場合だけ正常候補全件を1 Transactionで登録する。登録してからDELETEして帳尻を合わせる方式は使わない。行検証エラー0件でも候補数と総行数が一致しない等の内部不整合は登録禁止・RecoveryRequiredとする。

| 入力・結果 | MeasurementDataへの登録 | 配置・監視 |
|---|---|---|
| 正常5行 | 5行を一括commit | success、次ファイルへ |
| 正常3行＋異常2行 | 0行、AddRange未呼出し | error、後続中断、異常停止 |
| CSV内重複／DB既存重複／業務エラー1行以上 | 0行 | error、後続中断、異常停止 |
| Parser上正常な空CSV／ヘッダーのみ／データ0行 | 0行 | success、「データ0件で正常終了」、継続 |
| CSV解析／通常読込エラー（DB未実行が確定） | 0行 | errorへ移動を試み異常停止。移動不可なら保留 |
| 書込み中／共有違反 | 対象と後続とも未実行 | 全て直下残置、当該周期終了、監視継続、次周期は同じ先行CSVから再試行 |
| DB障害／commit不明／Journal不整合 | 0行または全行か不明。0件と断定しない | error移動禁止、直下保留、RecoveryRequired、異常停止 |
| DB確定後のファイル移動失敗 | 確定済み結果を維持 | MovePending、安全停止、移動だけ復旧 |
| ログ記録失敗のみ | 確定済み登録／全件拒否を変更しない | 確定したsuccess/errorへ移動し、未記録を表示して停止 |

周期の通常結果はTotalCount=読込総行数、SuccessCount=実登録行数、FailureCount=未登録行数とする。5行中2行の業務エラーで全件拒否なら5／0／5。別途ValidationErrorRowCount=2、HeldValidRowCount=3を結果DTO／状態に持ち、「エラー2行のため5行全件未登録」と表示する。ErrorLogへは実際の不正行だけを記録する。正常な3行に偽のValidationエラーを作らない。

手動は既存どおり5／3／2。既存DTO／OperationLog列の意味を手動側で変えない。DB結果不明の件数は成功0と装わず、状態・Journalで不明と明示する。

## 6. 停止・復旧・時系列

通常エラー時の確定フロー：

```text
A正常 → 全件登録 → success
B異常 → 登録0件 → エラー内容記録 → error
       → 後続と新規周期の開始を禁止 → 異常停止
C     → 未処理、監視直下に残る
```

Bのエラー検出時点で停止要求を確定し、error移動完了を待つ間にも次ファイル／次周期を開始しない。Aの登録結果はRollbackしない。All-or-Nothingの境界は1CSVであり、バッチ全体ではない。

時系列順序とは、通常の更新日時・名前順で既に確定した順序を、後続CSVが追い越さないことである。CSV行内の取得日時を並べ替える意味ではない。Journalに未完了の順序があれば、現在の更新日時で再ソートせずそれを優先する。新着ファイルは既存の未完了順序の後で、通常キーで次の順序を確定する。

A書込み中・B/C読取可能なら、その周期はA/B/Cすべて未登録で残す。次周期もAが先頭。A完成で更新日時がB/Cより新しくなってもA→B→Cを維持する。通常停止・アプリ再起動後も同じ順序記録を利用する。

Bの全件未登録が確定してerror移動した場合、順序記録はBの位置で「修正版待ち」とする。B修正版の更新日時がCより新しくても、B修正版→Cを優先する。再配置した修正版は新規Attemptとし、元Attemptとの関連をJournalへ保存する。

修正版の対応付けは、停止中のユーザー操作で元Attemptを表示し、監視直下の候補CSVを選択・確認する。ファイル名は案内に使うだけで同一性の根拠としない。選択時の指紋、ルート、ConfigId・設定スナップショット、元Attemptとの関連を保存し、実処理時に再照合する。未完了順序の後続枠に既に割り当てられた候補、別の未解決Attempt、成功確定済みファイルは修正版に選べない。

修正版が未選択、対応不明、候補が変更された場合は「修正版の確認待ち」としてStoppedを維持し、Cを処理しない。対応付け保存だけでは開始せず、ユーザーが開始を押す。修正版が正常登録または正常0行でsuccessへ移動し、Journalで正常完了が確認できた後だけCを許可する。再度通常エラーなら0件登録→error→異常停止、修正版待ちを維持する。詳細は基本設計§6.5・7.6。

DB障害／commit結果不明／Journal不整合時：

```text
新規処理禁止 → 元CSVを移動せず保留
 → RecoveryRequiredを可能な限り記録 → 異常停止
 → 人がCSV・DB・Journalを照合 → 解決後に手動再開始
```

Journalは監視直下の.periodic-importに保存する。ResultKnown／MovePendingの元CSVは再取込しない。ImportStartedのまま再起動した場合は結果不明として止める。未解決Attemptがある間は新規CSVを処理しない。ただし全件未登録が確定した修正版待ちでは、明示対応付けした修正版だけを処理できる。DB結果不明を修正版待ちと扱わない。Completedは30日保持するが、未完了順序・修正履歴から参照される記録と未解決記録は期限で削除しない。

利用者による管理フォルダ削除・改変の完全な自動検出は保証外。LocalAppDataとの突合は行わない。将来USER_GUIDEに「.periodic-importを削除・編集しない。異常時はCSV・DB・Journalを保全して照合する」と記載する。今回USER_GUIDE自体は変更しない。

## 7. UI・非機能要件

- MainFormの現行検索行・操作行・Gridを維持し、モード行と周期パネルを追加。手動モードでは周期パネルを折り畳む。
- 現行ClientSize 1180×680、MinimumSize 1100×640を基準とし、DPI・狭い表示を実機確認する。
- 監視中／停止中の操作制限はFR-15・23。Button無効化とイベント入口の状態確認を併用する。
- 履歴はDropDownList、最大100件、現在状態は独立Label。同種スキップを集約し、通知キューも有界にする。
- 同期CSV／DB／ファイルI/Oをバックグラウンドで実行し、UIスレッドへ通知。1ファイルずつ順次処理する。
- ApplicationはSQLite／CsvHelper／WinFormsに依存しない。SQL・Migration・ファイル実装はInfrastructure。Program.vb手動DI、既存NuGet固定を維持。
- 同一フォルダの監視所有者は1プロセス。旧版や外部ツールによるDB同時書込みを正式運用に含めない。
- タイマーはリアルタイム制御ではない。遅延した過去周期を連続再実行しない。1万行・多数CSVで時間／メモリ／停止応答を測定。
- 元CSVや既存フォルダの無条件上書き・削除、DB削除／再作成による移行は禁止。

## 8. 設定保存・DB互換性

CsvImportConfigへ以下の3列を追加する設計とする。

| 列 | 型・初期値 | 意味 |
|---|---|---|
| ImportMode | TEXT NOT NULL DEFAULT 'SingleFile' | SingleFile／PeriodicFolderのみ |
| WatchFolderPath | TEXT NULL DEFAULT NULL | 未設定可。周期開始時は有効なローカル通常フォルダ必須 |
| WatchIntervalSeconds | INTEGER NOT NULL DEFAULT 60 | 1～604800の整数 |

既存行は手動モード・未指定フォルダ・60秒となり、既存CSV形式／Mappingを維持する。Running／Starting／Stoppingは列にしない。

MainFormでCSV設定を選ぶと、その設定に紐づく監視値を表示する。停止中の「監視設定保存」で3項目を保存する。開始時は検証・保存が成功してから監視する。既存CSV設定画面はCSV形式とMappingだけを更新し、監視3列を初期値で上書きしない。

現行にMigration／DB Schema Version管理は確認できないため、PRAGMA user_versionと実Schema検証による追加専用Migrationを設計する。Ver1.00相当の未版管理DBは既存構造を検証し、整合したバックアップを取得後、3列追加とuser_version更新を同一Transactionで確定する。新規DBは最初から拡張Schema、既存DBはテーブル削除・再作成なし。詳細は基本設計§9。

Ver1.00 DBをVer1.10で開いて既存データを引き継ぐ互換性を保証対象とする。更新済みDBを旧EXEで継続運用する後方互換は保証しない。旧版へ戻す場合は移行前バックアップを別途保管し、移行後データの扱いを確認する。

## 11. J-01最終改訂の範囲

Journalに単一の未完了順序記録と修正版対応付け情報を追加する。ファイルのLastWriteTimeUtcの変更、後続CSVの勝手な移動、Journal削除による解除、成功確定済みAttemptの再登録、自動監視再開は禁止。DB結果不明／Journal不整合は元CSV保留→RecoveryRequired→停止を維持する。

Phase 4に順序保持・書込み中後続保留・修正版優先・Journal順序復旧を追加し、Phase 1～3の実装範囲は拡大しない。テスト計画T01～T64を維持・更新し、T65以降に境界試験を追加する。今回変更するのは本書と基本設計書のみ。
